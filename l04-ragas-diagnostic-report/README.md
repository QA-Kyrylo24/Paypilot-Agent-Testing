- 2-га версія (переформульована на `fraud_card_not_present`, унікальну фразу з `reason-codes.md`) наживо пройшла один раз (трейс `8ebef591`), але при повторному прогоні через кіт модель склала інший пошуковий запит і той самий факт випав із топ-4 (трейс через звіт `golden-clean-20261028T185354.json`) — виявилось, що ранжування для цього факту нестабільне саме через недетермінізм формулювання запиту моделі, а не через профіль.
- 3-тя версія (`service-levels.md`, години роботи людей-агентів) — перевірена на стійкість шістьма різними формулюваннями запиту напряму через `retriever.search(..., index="kb_clean"/"kb_broken")`: перемагає в топ-1 щоразу, з запасом за score, на обох індексах. Розбіжність із прогнозом: **9 з 12 (75%) збіглися**, 3 — ні, і для кожної є конкретна причина, видна з трейсу:
- `RET-H02` (прогноз: впаде) — **не впав**. Перший пошук, як і передбачалось, приніс `disputes.md#b1` (вступний чанк без таблиці) — але цього разу агент сам зробив другий, інакше сформульований пошук («chargeback window by reason code duplicate_charge»), і він приніс `disputes.md#b2` (score 1.0, таблиця ціла). Прогноз врахував лише перший пошук; не врахував, що агент іноді перепитує з іншим формулюванням і тим рятує себе сам — це не стабільна поведінка (не можна покладатись на повторний пошук як на гарантію), але в цьому конкретному прогоні він відбувся.
- `RET-H03` (прогноз: не впаде) — **впав**. Для вправи 1 (комбінований запит «spread + allowance») `tariffs.md#b3` стабільно вигравав топ-1 — звідси й прогноз. Але RET-H03 питає лише про спред, і агент склав коротший пошуковий запит («FX spread by customer tier»), який замість `tariffs.md#b3` притягнув `glossary.md#b5` (загальне визначення терміна «Tier», без жодних цифр). Прогноз неправомірно переніс висновок з іншого (ширшого) формулювання запиту на вужче, не перевіривши це нове формулювання окремо — на відміну від `RET-H07`, де саме така перевірка (`retriever.search` із варіаціями запиту) і врятувала прогноз.
- `RET-H08` (прогноз: не впаде) — **впав**. Пошук («contactless card payment PIN required») притягнув `security-policy.md#b2`, бо той теж згадує слово «PIN» (в іншому контексті — заборона питати PIN у підтримці), а не `cards.md#b3` із самим фактом. Той самий клас проблеми, що зламав першу версію `RET-H07` (два документи з словом, яке шукаємо, перемагає не той) — але для `RET-H08` я не прогнав `retriever.search` із варіаціями запиту заздалегідь, хоча для `RET-H07` саме це і зробив після першого провалу. Методологічний висновок: прогнози, перевірені `retriever.search` із кількома формулюваннями до прогону, збулися всі (`RET-H07`, `RET-H10`); ті, що спирались на аналогію з іншим кейсом без прямої перевірки (`RET-H03`, `RET-H08`), помилились обидва рази.
