**3**. Діапазон моменту прояву — **5-7**, або відсутній.

крок **3** — за кількістю кроків із початку діалогу, не за загальною

кроків) усі однаково перетинають межу вже на кроці 3, тож подовження
сценарію понад 3 кроки не додає безпеки. Рішення: довіряти пам'яті
агента про сутності справи без повторної перевірки інструментом можна
лише в межах перших 2 кроків діалогу.

## 3.1 — Крок втрати і доказ причини

На основі прогону №1 `lesson-05`:

- **Крок втрати:** 3 — `agent.summarize` дав розмитий переказ без
  зв'язки "ця справа = TX-0401" (сума 240 пізніше не губилась,
  губилась прив'язка до конкретної транзакції).
- **Крок прояву:** 5 — агент прямо сказав: "I can't tell from our
  conversation which one is the payment for goods that never arrived,
  so I won't assume" (бачить обидві 240 EUR транзакції, забув, яка
  саме обговорювалась).
- **Перевірка даних кроку прояву:** `get_transactions` повернув повні
  й коректні дані — інструмент/пошук не винен, причина суто в
  пам'яті діалогу.
- **Висновок:** D06. Втрата — крок 3, прояв — крок 5.

**Прогін №2 — окремий випадок:** крок втрати теж 3, доведено буквально
(переказ замінив `goods_not_received` → `service_not_rendered`), але
крок прояву в цьому прогоні **не настав**: агент на кроках 5-7 сам
повторно звернувся до інструментів і видав правильні факти клієнту.
Момент втрати стався, але замаскувався, перш ніж дійшов до клієнта.

## 3.2 — Самосуперечність

Дві репліки агента про **строк подання спору** (прогін №5):

- **Крок 2:** "The checks passed… The window closes on **2026-10-18**
  (90 days from the transaction date)."
- **Крок 7:** агент знову звертається до пошуку (`disputes.md#s1`) і
  каже: "TX-0401 (2026-07-20)… about 57 days ago:
  **duplicate_charge (60-day window): still open, with about 3 days
  left**."
- **Суперечать?** Так — 90 днів/18 жовтня (крок 2) проти 60-денного
  вікна за ~3 дні (крок 7), для **тієї самої** TX-0401.
- **Перевірка входу кроку 7:** пошук викликався знову (та сама повна
  таблиця) — контекст цілий, пошук не винен. Reason code,
  зафіксований на кроці 1-2 (`goods_not_received`), до цього моменту
  вже підмінений переказом кроку 3 (`service_not_rendered`) — агент
  замість пригадування вже встановленого факту почав **перебирати
  кандидатів заново**, і один із них (`duplicate_charge`, 60 днів)
  протік у відповідь.
- **Класифікація: D07 поверх D06** — сутність (reason code) зникла
  раніше (крок 3), суперечність по строку проявилась значно пізніше
  (крок 7).

**Побічна знахідка:** у тому самому прогоні №5 на кроці 6 вже була й
суперечність по **reason code** ("goods_not_received" на кроках 1-2
проти "service_not_rendered" на кроках 3,6-7) — інша сутність, D07
без "поверх D06" (код не зник, а замінився одним значенням і лишався
тим самим далі).

## 3.4 — Механізми збою на решті сценаріїв плану

### `CONV-H02` (5 кроків) — D06 + D07 разом

Доказ — `summary.text` кроку 3 (не текст відповіді клієнту):
> "...TX-0401 (EUR **180.00**)... The code is **service_not_rendered**."

Сума (240→180) і код (`goods_not_received`→`service_not_rendered`)
зіпсовані в самому переказі, одночасно. Крок втрати: 3. Крок прояву:
5 (агент сам зауважив розбіжність і перепитав). Класифікація: **D06
(сума) + D07 (код)** — той самий комбінований механізм, що й на
основному сценарії, лише сильніший прояв.

### `CONV-H03` (10 кроків) — D07

Доказ — `summary.text` кроку 3: "...The applicable reason code is
**service_not_rendered**. Eligibility checks passed..." — підміна
прямо прив'язана до справи, без невизначеності. На кроці 10 агент сам
ловить суперечність: "The reason code I have checked... is
**goods_not_received**... Earlier, the reason code on record was
**service_not_rendered**...".

Класифікація: **D07**, крок втрати **3**, крок прояву **10** (median
10, range 10-10 — питання про код на цьому сценарії задають саме на
останньому кроці).

### `CONV-H05` (7 кроків, без перемикання теми) — D07, не retrieval

- **Крок 3, `summary.text`:** "...The assistant identified the
  **"service_not_rendered"** code and confirmed the transaction is
  eligible..." — код уже зіпсований у переказі, до того, як клієнт
  щось почув.
- **Крок 7 (момент прояву), повний трейс ходу:** лише `agent.request`
  → `llm.call` — **жодного** `tool.*` чи retrieval-спану. На кроці
  прояву агент нічого не шукав і нічого не перевіряв — відповідь
  («The reason code is **service_not_rendered**...») побудована
  виключно на зіпсованій історії з кроку 3.

Класифікація: **D07**, крок втрати **3**, крок прояву **7**. Пошук
(retrieval) тут виключений прямо — на кроці 7 retrieval-спану в трейсі
просто немає.

## 5. Тест-план і ціна

### Три осі

| Вісь | Значення | Що саме ловить |
|---|---|---|
| Довжина | 5 · 7 · 10 кроків | чи поріг згортки (`summarize_after=2`) спрацьовує незалежно від довжини сценарію |
| Кількість сутностей | 1 · 2 · 3 | конкуренцію за місце в переказі: сума; сума+код; сума+код+друга транзакція з тим самим ключовим атрибутом |
| Перемикання теми | 0 · 1 · 2 | чи агент повертається до параметрів справи після відхилення (card limit, FX) |

Повна комбінаторика: 3 × 3 × 3 = **27 сценаріїв**. Ціна одного повного
прогону набору (1 раз кожен сценарій) = сума довжин по всіх
комбінаціях: кожне з 3 значень довжини зустрічається в 9 комбінаціях
(3 сутності × 3 перемикання) → (5+7+10) × 9 = **198 викликів**. З
вимогою ≥5 прогонів на сценарій (через ймовірнісність дефекту) —
**990 викликів** на один повний прогін набору.

### Обрані сценарії

| ID | Довжина | Сутності | Перемикання | Роль у плані | Результат |
|---|---|---|---|---|---|
| `CONV-H01` | 7 | 2 | 2 | основний, = C-07 | `clean` 5/5; `lesson-05` reason code 2/10 |
| `CONV-H02` | 5 | 2 | 2 | ізоляція осі (довжина) | `clean` 5/5; `lesson-05` reason code 4/5 |
| `CONV-H03` | 10 | 2 | 3 | найгірший | `clean` 5/5; `lesson-05` reason code 2/5 |
| `CONV-H04` | 2 | 1 | 0 | контроль | `clean`/`lesson-05` 5/5 обидва — нижче порогу згортки, дефект структурно неможливий |
| `CONV-H05` | 7 | 3 | 0 | ізоляція осі (сутності) | `clean` 5/5; `lesson-05` reason code 1/5 |

`CONV-H03` і `CONV-H04` свідомо виходять за межі заявленої сітки
значень (перемикання=3, довжина=2) для своєї ролі — найгіршого
випадку й контролю нижче порогу.

### Ціна обраного плану

Кроки × прогони (5 на кейс) × сценарії:

`CONV-H01`: 7×5=35 · `CONV-H02`: 5×5=25 · `CONV-H03`: 10×5=50 ·
`CONV-H04`: 2×5=10 · `CONV-H05`: 7×5=35

**Разом: 155 викликів** на один повний прогін набору на `lesson-05`.
Проти 990 викликів повної комбінаторики — обраний план коштує ~16% від
повного покриття.

### Ціна в грошах (`claude-haiku-5-5`: $0.10 / Mtok вхід, $0.50 / Mtok вихід)

| Кейс | $ (5 прогонів) |
|---|---|
| `CONV-H01` | $0.0388 |
| `CONV-H02` | $0.0301 |
| `CONV-H03` | $0.0454 |
| `CONV-H04` | $0.0079 |
| `CONV-H05` | $0.0368 |

**Разом: ≈ $0.16** за один повний прогін усіх 5 сценаріїв. Повна
комбінаторика (990 викликів): ≈ $1–1.5. При такій дешевій моделі гроші
не є обмеженням плану — реальна ціна покриття — кількість запитів і
шум у звіті, не бюджет.

### Коли проганяти набір

**Лише перед релізом, не щодня.** `l05_dialogs.jsonl` вимагає
`runs: 5` на кейс через ймовірнісність дефекту — п'ять повних діалогів
замість однієї репліки, тобто в рази дорожче за звичайний рядок
`golden.jsonl`. $0.16 на прогін сама по собі не причина уникати
щоденного gate (сума мізерна) — справжня причина ймовірнісність:
щоденний прогін на 5 повторах дає шум ("сьогодні впало, завтра ні" без
жодної зміни коду), з яким команді нема що робити щодня; раз перед
релізом — досить, щоб побачити розподіл і прийняти рішення. Дешеві
детерміновані перевірки (трейс, `has_span`) лишаються в щоденному
gate; повний діалоговий набір із 5-разовим повтором — лише в
release-gate (звідси `"gate": "release"` у схемі кейса).

## 6. Залишковий ризик і рішення

### Непокриті комбінації осей

З 27 клітинок сітки (3×3×3) план накриває 3 всередині сітки
(`CONV-H01`=(7,2,2), `CONV-H02`=(5,2,2), `CONV-H05`=(7,3,0)) плюс 2
поза сіткою для стрес-тесту меж (`CONV-H03`, `CONV-H04`). Лишається 24
клітинки непокритими. Три найважливіші:

| Що не покрито | Що станеться, якщо зламається | Чому живемо з цим зараз | Рішення |
|---|---|---|---|
| (10, 3, 2) — найгірший випадок на всіх трьох осях одночасно | Найсильніший можливий прояв D06/D07 лишиться непоміченим до першої реальної скарги клієнта з таким профілем діалогу | `CONV-H03` уже проксі для (довжина+перемикання), `CONV-H05` — проксі для (сутності); повна комбінація всіх трьох максимумів одразу — комбінаторний ріст ціни без нової інформації про механізм (той самий D06/D07, що й у вже перевірених клітинках) | **Відкласти** — додати, якщо з'явиться скарга з профілем, близьким до цієї клітинки |
| (5, 1, 0) — короткий, максимально простий діалог | Якби дефект проявлявся навіть тут, це означало би, що довжина взагалі не захищає | `CONV-H04` (2,1,0) уже перевіряє нижню межу довжини; `CONV-H02` (5,2,2) перевіряє ту саму довжину зі складнішим навантаженням, і дефект там є — якщо він є при вищій складності, спрощення малоймовірно додасть новий ризик | **Прийняти** |
| (10, 1, 0) — довгий діалог, мінімальна складність | Невідомо, чи прибирання складності при тій самій довжині 10 підвищує чи знижує вже підтверджену частку прояву | `CONV-H03` (10,2,3) показує D07 у 2/5 прогонів — ризик на довжині 10 реальний і підтверджений; ця клітинка лишається непокритою не тому, що ризику немає, а тому що невідомий напрямок впливу складності | **Відкласти** |

### Сліпа зона методу

**Узгоджена помилка.** Інваріант перевіряє лише "чи значення не
змінилось між кроками" — не "чи воно було правильним із самого
початку". Агент, що на кроці 1 назвав хибну суму чи код і стабільно
повторює те саме хибне значення всі 7 кроків, пройде кожен інваріант у
`l05_dialogs.jsonl` на зелено.

**Чим закриваємо.** Оракулом — не додатковим інваріантом. У кожному
інваріанті `oracle_turn`/`oracle_by` обов'язкові для всіх п'яти
кейсів — структурно неможливо додати інваріант без оракула, який
звіряє значення на `oracle_turn` із джерелом правди (`engine:disputes`
чи `kb:disputes.md#s1`), а не лише між кроками.

### Вибір виправлення D06

Обрано: **«Винести сутності справи поза згортку, у структуроване
поле»**.

**Ціна:** правка коду оркестрації — сума спору й reason code
зберігаються в окремому структурованому полі сесії (не в тексті
переказу) і підставляються в кожен крок напряму, незалежно від того,
що написав сумаризатор.

**Чому не інші два:** підняти `SUMMARIZE_AFTER` не лагодить механізм —
лише відсуває крок, на якому він спрацює (крок 3 настає детерміновано
незалежно від довжини, піднятий порід просто зсуне ту саму проблему на
пізніший крок). Інструкція «зберігай числа» в промпті сумаризатора —
найдешевша, але рівно той механізм, що вже провалився
(`_transform_summary` підміняє текст незалежно від інструкцій моделі).

**Побічна плата:** потрібно наперед знати, які сутності важливі — але
це вже є, це сума + reason code з тест-плану вище, не нова невідома.

### Підсумковий рядок

**Що обміняли:** ширину покриття (3 клітинки сітки всередині + 2 поза
нею, замість усіх 27) на швидкість і дешевизну (155 викликів ≈ $0.16
замість 990 ≈ $1–1.5).

**Чого не робимо:** не перевіряємо потрійний найгірший випадок
(10,3,2); не змінюємо код оркестрації під обраний фікс D06 — лише
названо й оцінено ціну, саму правку не внесено.

**За яких умов рішення зміниться:** якщо на release-gate частка
червоних прогонів (`CONV-H01`/`H02`/`H05` разом) перевищить ~20% на
`lesson-05` протягом кварталу — це сигнал переходити від «відкласти» до
рішення про фікс.
